# Module 1.1, Session 2: Growing Things

Unit 1: Systems programming · 2026-11-24

The arena never grows: it hands out pieces of one fixed buffer. This session builds the two containers that do grow, a dynamic array and a hash map. Most of C's container bugs live in the same few places: overflow in the size arithmetic, `realloc` handling, and pointers that outlive the memory they point into.

## Mini-lesson

### 1. Dynamic array: length vs capacity

A dynamic array keeps three things: a pointer to a heap buffer, the **length** (elements in use) and the **capacity** (elements the buffer can hold). A push writes at index `len` if `len < cap`; otherwise it grows the buffer first.

```
data ──► [ a | b | c | d | . | . | . | . ]
           len = 4          cap = 8
```

**Grow geometrically, not by a constant.** If every growth adds a fixed 16 slots, pushing n elements copies about n²/32 elements in total: quadratic. If every growth doubles the capacity, the copies add up to at most about 2n, so each push is O(1) **amortized**: an occasional expensive push pays for itself across the cheap ones. Factors between 1.5 and 2 are common; any factor above 1 gives amortized O(1).

### 2. Making the array generic in C

C has no generics. The common way to write one container for any element type is to store the **element size** and move bytes:

```c
Vec *v = vec_create(sizeof(struct point));
struct point p = { 3, 4 };
vec_push(v, &p);                          /* copies sizeof(struct point) bytes */
struct point *q = vec_get(v, 0);
```

Inside, element `i` starts at byte `i * elem_size` of the buffer. You can't do arithmetic on a `void *` in standard C (gcc allows it as an extension, `-Wpedantic` warns), so cast to `char *` (or `unsigned char *`) first: one `char` is one byte. Copy elements with `memcpy`.

### 3. `realloc`: three traps

**Trap 1: losing the buffer on failure.**

```c
v->data = realloc(v->data, new_bytes);    /* BUG */
```

When `realloc` fails it returns `NULL` and **leaves the old block alone**. This line overwrites your only pointer to the old block with `NULL`: the elements are gone and the old buffer leaks. Assign to a temporary, check it, then commit. After a failed push, the array must still hold exactly what it held before.

**Trap 2: overflow in the size.** `new_cap * elem_size` can wrap, exactly like the arena's `offset + size`. A wrapped product is a small number, `realloc` happily succeeds with a tiny buffer, and the next `memcpy` writes far past its end. Check before you multiply, using the same idea as the arena: compare against a limit in a way that can't itself overflow. Doubling `cap` can overflow too.

**Trap 3: pointers into the buffer go stale.** `realloc` may move the block. Any pointer you got from `vec_get` before a push that grew the array now points into freed memory. That's a **use-after-free**, and ASan names it:

```
ERROR: AddressSanitizer: heap-use-after-free on address ...
```

This is why C++'s `std::vector` documents "iterator invalidation" and why Rust's borrow checker forbids holding a reference into a `Vec` while you push to it. Keep this one in mind for Bridge A.

### 4. Hash map: open addressing with linear probing

A hash map turns a key into an index with a **hash function**, then stores the entry in an array of **slots** at that index. Two keys can land on the same slot (a **collision**). There are two families of fixes:

- **Chaining:** each slot holds a linked list. Simple, but every entry is a separate allocation and lookups chase pointers.
- **Open addressing:** every entry lives in the slot array itself. On a collision, try the next slot, then the next (**linear probing**), wrapping at the end. One allocation, and probes walk adjacent memory, which caches love (Module 1.5 explains why).

Build the open-addressing version.

**Capacity as a power of two.** With `cap = 2^k`, `hash % cap` equals `hash & (cap - 1)`: the same identity as your padding bit trick.

**Hash function: FNV-1a.** Simple, decent, and enough here. For 64 bits:

```
h = 0xcbf29ce484222325           (offset basis)
for each byte b of the key:
    h = h XOR b
    h = h * 0x100000001b3        (FNV prime; let it wrap, so use uint64_t)
```

Unsigned multiplication wraps by definition, so this is well defined. The same code with a signed type would be UB.

**Load factor.** `count / cap`. As it approaches 1, probe sequences get long and an insert into a full table never finds a slot. Grow (double `cap`) before the load factor passes about 0.7. **Growing means re-inserting every entry**: each key's index depends on `cap`, so you can't copy the slot array as it is.

**Deletion is the hard part.** Lookup for key K walks from K's home slot until it finds K or hits an **empty** slot, which means "K isn't here." Suppose A and B both hash to slot 3, so A sits in 3 and B in 4. Delete A by marking slot 3 empty, and a lookup for B now stops at slot 3 and wrongly reports B missing. Two standard fixes:

- **Tombstones:** mark a deleted slot as "deleted", not empty. Lookups walk past it; inserts may reuse it. Tombstones fill the table too, so count them toward the load factor when deciding to grow, and drop them when you rehash.
- **Backward-shift deletion:** after emptying a slot, walk forward and move later entries back into the gap when that keeps them reachable from their home slot. No tombstones, but trickier to get right.

Pick one. Your tests decide whether you got it right.

**Who owns the key?** If `map_put` stores the caller's `const char *` pointer, the map breaks as soon as the caller reuses or frees its buffer. Copy the key into memory the map owns (`malloc` + `memcpy`, or `strdup`, which is POSIX and standard only from C23), and free it on removal and in `map_destroy`.

### 5. Make, grown up: pattern rules and header dependencies

Two practicums with two test programs in one folder is where the session 1 Makefile starts to repeat itself. Here is the `mathx` example rewritten so each `.c` compiles to its own `.o`, and only changed files rebuild. It was run in Debian, and the outputs below are real.

```make
CC       = gcc
CFLAGS   = -std=c17 -Wall -Wextra -Wpedantic -g -MMD -MP
SANFLAGS = -fsanitize=address,undefined -fno-sanitize-recover=all

.PHONY: all test clean

all: test_mathx

test_mathx: test_mathx.o mathx.o
	$(CC) $(CFLAGS) $(SANFLAGS) -o $@ $^

%.o: %.c
	$(CC) $(CFLAGS) $(SANFLAGS) -c -o $@ $<

test: test_mathx
	./test_mathx

clean:
	rm -f test_mathx *.o *.d

-include $(wildcard *.d)
```

What's new:

- **`%.o: %.c`** is a **pattern rule**: "any `X.o` is built from `X.c` with this recipe." `-c` means compile only, don't link.
- **`$<`** is the first prerequisite (the `.c`); **`$^`** is all of them (both `.o` files for the link).
- **`-MMD`** makes gcc write a `.d` file next to each `.o` listing the headers that `.c` actually included. You stop listing headers by hand:

  ```
  $ cat mathx.d
  mathx.o: mathx.c mathx.h
  mathx.h:
  ```

- **`-MP`** adds the empty `mathx.h:` rule. Without it, deleting or renaming a header breaks the build with "No rule to make target 'mathx.h'" until you `make clean`.
- **`-include $(wildcard *.d)`** pulls those rules into the Makefile. The leading `-` means "fine if there are none yet," as on a fresh checkout.

What that buys you:

```
$ touch mathx.c && make           # only mathx.o recompiles, then the link
gcc ... -c -o mathx.o mathx.c
gcc ... -o test_mathx test_mathx.o mathx.o

$ touch mathx.h && make           # both .c files include it, so both recompile
gcc ... -c -o test_mathx.o test_mathx.c
gcc ... -c -o mathx.o mathx.c
gcc ... -o test_mathx test_mathx.o mathx.o
```

One catch: **`.o` files remember the flags they were built with.** Make only compares timestamps, so `make CC=clang` after a gcc build relinks the old gcc objects. Run `make clean` when you switch compiler or flags.

### 6. valgrind, and why it doesn't mix with ASan

valgrind runs your unmodified binary on a simulated CPU and checks every memory access: leaks, use-after-free, reads of uninitialized memory. It's slow (10 to 50 times), but it needs no recompile, so it works on binaries you can't rebuild with sanitizers. Useful flags:

```
valgrind -q --leak-check=full --error-exitcode=1 ./test_vec
```

`--error-exitcode=1` matters for the same reason `-fno-sanitize-recover=all` did: without it, valgrind exits with your program's status even when it found errors.

**Never run valgrind on an ASan binary.** Here is what happened in Debian when I tried:

```
$ valgrind -q --leak-check=full --error-exitcode=1 ./test_mathx
==6876==ASan runtime does not come first in initial library list; ...
$ echo $?
0
```

The ASan runtime refused to start, so **the tests never ran**, and valgrind still exited 0. A green result that tested nothing: the same failure shape as UBSan without `-fno-sanitize-recover`. A valgrind build needs its own objects compiled **without** `$(SANFLAGS)`.

### 7. gdb, just enough

When a test fails and you can't see why, run it under gdb. Your `-g` flag already put the source-line information in.

```
gdb ./test_map
(gdb) break map_remove        # stop when this function is called
(gdb) run
(gdb) bt                      # backtrace: who called whom
(gdb) next / step             # next line; step into a call
(gdb) print *m                # print a whole struct
(gdb) print m->slots[5]       # or one slot
(gdb) continue
```

`gdb -tui` splits the screen and shows the source as you step. You'll live in gdb during the Bomb Lab in 1.3, so getting comfortable now pays off.

## Practicum

Work in a new folder, `unit1/1.1-c/containers/`, with one Makefile for both containers. This is a two-week practicum; do the dynamic array first.

### Part A: dynamic array (`vec.h`, `vec.c`, `test_vec.c`)

```c
typedef struct Vec Vec;
Vec   *vec_create(size_t elem_size);         /* NULL if elem_size == 0 or out of memory */
void   vec_destroy(Vec *v);
size_t vec_len(const Vec *v);
void  *vec_get(Vec *v, size_t i);            /* NULL if i >= len */
bool   vec_push(Vec *v, const void *elem);   /* copies elem_size bytes; false on failure */
bool   vec_pop(Vec *v, void *out);           /* copies the last element to out; false if empty */
```

### Part B: hash map (`map.h`, `map.c`, `test_map.c`)

String keys, `int` values:

```c
typedef struct Map Map;
Map   *map_create(void);
void   map_destroy(Map *m);
size_t map_len(const Map *m);
bool   map_put(Map *m, const char *key, int value);  /* copies key; overwrites an existing key's value; false on failure */
bool   map_get(const Map *m, const char *key, int *out);
bool   map_remove(Map *m, const char *key);          /* false if key not present */
```

**Done when:**

- [ ] **vec:** tests push and pop at least 1,000,000 `int`s and check every value. They also cover a struct element type, `vec_get` past the end returning `NULL`, and `vec_pop` on an empty array returning `false`.
- [ ] **vec:** growth is geometric, and an impossible request fails cleanly. Test: `vec_create(SIZE_MAX / 2)` either returns `NULL` or returns an array whose pushes fail with `false` and leave `vec_len` unchanged. No crash and no sanitizer report.
- [ ] **map:** put, get, overwrite (`map_len` doesn't change), and remove work. Getting a missing key and removing a missing key both return `false`.
- [ ] **map:** insert 100,000 distinct keys (e.g. `"key0"` to `"key99999"`, built with `snprintf`), then check that every key returns its value. That proves resizing re-inserts correctly.
- [ ] **map:** remove every other key from that set, then check that each removed key is gone and **each remaining key is still found**. That's the deletion trap from the mini-lesson. Then insert new keys and check that everything is still consistent.
- [ ] **map:** keys are copied. Put a key from a `char[]` buffer, overwrite the buffer, and the original key is still found.
- [ ] `make test` builds both test programs with the session 1 flags, using a `%.o: %.c` pattern rule and `-MMD -MP`, and passes under `CC=gcc` and `CC=clang` (run `make clean` in between).
- [ ] `make valgrind` builds separate, sanitizer-free test binaries and runs both under `valgrind -q --leak-check=full --error-exitcode=1`, clean. Hint: give those binaries their own object files. A `build/` subfolder per variant, or compiling the `.c` files straight into the binary, both work.
- [ ] Stretch: watch ASan catch the stale-pointer trap. In a separate file outside `make test`, take `int *p = vec_get(v, 0)`, push until the array grows, then read `*p`. Then the same with valgrind on a plain build. Compare the two reports.
- [ ] Stretch: the session 1 arena stretch (chained blocks), or back the map's key copies with an arena so `map_destroy` frees them all at once.

`.gitignore` now ignores `*.d` along with `*.o`; run `git pull` before you start.
