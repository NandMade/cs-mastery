## 1. What an arena allocator is

An arena (also called a bump allocator or linear allocator) is the simplest useful allocator:

1. **Create:** get one big buffer up front. Keep an offset into it, starting at 0.
2. **Alloc:** round the offset up so the next object is correctly aligned, hand out a pointer there, and advance the offset by `size`. If the request doesn't fit, return `NULL`.
3. **Free:** there is no per-object free. `arena_reset` puts the offset back to 0, which frees everything at once and keeps the buffer. `arena_destroy` gives the buffer back.

```
buffer: [ obj A ][pad][ obj B ][ obj C ]                ...free...       ]
        ^                                ^                                ^
        start                            offset (next alloc starts here)  end
```

Allocation is a few arithmetic operations, and you can't leak or double-free individual objects. It fits any group of objects that die together: one request, one parse, one compiled function, one frame. You'll use arenas again in your compiler (AST nodes), your kernel, and your database (per-query memory). The catch: nothing is freed until the next reset.

## 2. Who decides `align`?

**Alignment belongs to the type of the object being allocated, not to the previous allocation.** The C standard gives every type an alignment requirement: its address must be a multiple of that number. You get it with `alignof(T)` from `<stdalign.h>` (or the keyword `_Alignof(T)`).

On x86-64 Linux (measured with gcc 14 in Debian):

| Type | `sizeof` | `alignof` |
|---|---|---|
| `char` | 1 | 1 |
| `short` | 2 | 2 |
| `int`, `float` | 4 | 4 |
| `long`, `double`, any pointer | 8 | 8 |
| `long double` | 16 | 16 |
| `max_align_t` | 32 | 16 |
| `struct { char c; double d; }` | 16 | 8 (its strictest member) |

The caller passes `align` because only the caller knows what it's going to store. The allocator only sees a byte count. A caller allocating a `double` writes:

```c
double *d = arena_alloc(a, sizeof(double), alignof(double));
```

That's tedious enough that arena libraries usually add a macro on the caller's side, like `#define ARENA_NEW(a, T) ((T *)arena_alloc((a), sizeof(T), alignof(T)))`.

### Padding depends on where you are and what comes next

The padding before an object depends on two things: where the offset currently sits, and the alignment of the object being placed *now*. Walk through four allocations:

| Call | Offset before | Padding | Object at | Offset after |
|---|---|---|---|---|
| `char` (size 1, align 1) | 0 | 0 | 0 | 1 |
| `double` (size 8, align 8) | 1 | 7 | 8 | 16 |
| `char` (size 1, align 1) | 16 | 0 | 16 | 17 |
| `int` (size 4, align 4) | 17 | 3 | 20 | 24 |

Note that the padding before the second `char` is 0, even though the previous object was 8 bytes.

### Why "always pad to 8" isn't enough

Padding to a fixed 8 after every allocation has two problems, plus a bug in the formula itself:

- **It wastes space.** A run of `char` allocations would each burn 8 bytes.
- **It isn't enough.** `long double`, `max_align_t`, SSE vectors (16) and cache-line-aligned structs (64) need more than 8.
- **The formula has an off-by-one.** `8 - offset % 8` gives 8 when the offset is already aligned, where the right answer is 0. Watch for this in your own rounding.

`malloc` takes the fixed-alignment approach: it always returns memory aligned for `max_align_t` (16 on x86-64 glibc), so the caller never has to say. That's a fine design for a general allocator. Your arena's API asks for the precise alignment instead, so it wastes nothing.

### Why alignment matters on x86-64

x86 hardware tolerates most misaligned loads, so it's tempting to ignore. Don't:

- In C a misaligned access is undefined behavior. UBSan reports `misaligned address`, and the optimizer is allowed to assume it never happens.
- Aligned SSE instructions (`movaps`) fault on misaligned addresses, and compilers emit them for structs they believe are aligned.
- Misaligned atomics can be split across cache lines, which is slow and can lose atomicity.

### A question to settle before you write `arena_alloc`

Your done-when list checks `(uintptr_t)p % align == 0`, which is about the **address**, not the offset. Rounding the offset up only gives an aligned address if the buffer's start is itself aligned at least that strictly. `malloc` gives you a 16-aligned start. What happens when a caller asks for `align = 64`? Decide which one you round, and write a test with a large alignment that proves it.

## 3. Make in 15 minutes

`make` reads a `Makefile` describing **targets** (files to build), their **prerequisites** (files they're built from), and the **recipe** (shell commands that build them). It rebuilds a target only when it is missing or older than one of its prerequisites. That's the whole idea: a dependency graph plus file timestamps.

Here is a complete Makefile for a tiny library `mathx.c` with a test program `test_mathx.c`. It was run in Debian, and the outputs further down are real.

```make
CC       = gcc
CFLAGS   = -std=c17 -Wall -Wextra -Wpedantic -g
SANFLAGS = -fsanitize=address,undefined -fno-sanitize-recover=all

.PHONY: all test clean

all: test_mathx

test_mathx: test_mathx.c mathx.c mathx.h
	$(CC) $(CFLAGS) $(SANFLAGS) -o $@ test_mathx.c mathx.c

test: test_mathx
	./test_mathx

clean:
	rm -f test_mathx
```

Line by line:

- **`CC = gcc`** etc. are variables, used as `$(CC)`. Anything on the command line overrides them: `make CC=clang test` builds the same thing with clang. Try it with your arena.
- **`.PHONY: all test clean`** says these names are actions, not files. Without it, a file that happens to be called `test` would make `make test` think it's up to date and do nothing.
- **`all:`** is the first target, so plain `make` builds it.
- **`test_mathx: test_mathx.c mathx.c mathx.h`** means "rebuild the binary if any of these three is newer." List the header too, or editing it won't trigger a rebuild.
- **The recipe line must start with a real TAB character**, not spaces. Spaces give `*** missing separator. Stop.` This is make's most famous trap. Set your editor to keep tabs in Makefiles.
- **`$@`** is an automatic variable meaning "the target of this rule", here `test_mathx`.
- **`test: test_mathx`** builds the binary first if needed, then runs it. If the program exits nonzero, make prints `Error 1` and exits nonzero itself.

What that looks like:

```
$ make test                       # fresh: compiles, then runs
gcc -std=c17 -Wall -Wextra -Wpedantic -g -fsanitize=address,undefined -fno-sanitize-recover=all -o test_mathx test_mathx.c mathx.c
./test_mathx
all tests passed

$ make test                       # nothing changed: skips the compile, just runs
./test_mathx
all tests passed

$ touch mathx.h && make           # header "changed": rebuilds
gcc -std=c17 ... -o test_mathx test_mathx.c mathx.c
```

Real projects add pattern rules (`%.o: %.c`) so each `.c` compiles separately and only changed files rebuild, plus automatic header dependency tracking (`-MMD -MP`). You don't need either for a three-file practicum. You'll meet CMake, which generates build files for you, in Bridge B.

## 4. Testing C without a framework

In C, a test suite is just a program, and **its exit status is the verdict**: 0 means pass, anything else means fail. `make`, CI systems and shell scripts all understand that. You don't need a framework yet. Frameworks such as Unity, cmocka and Check exist, but a 10-line macro teaches you what they do for you.

```c
#include <stdio.h>
#include "mathx.h"

static int failures = 0;

/* Like assert, but records the failure and keeps going so one run shows every broken check. */
#define CHECK(cond)                                                          \
	do {                                                                 \
		if (!(cond)) {                                               \
			fprintf(stderr, "%s:%d: CHECK failed: %s\n",         \
				__FILE__, __LINE__, #cond);                  \
			failures++;                                          \
		}                                                            \
	} while (0)

static void test_clamp_below_and_above(void)
{
	CHECK(clamp_int(-3, 0, 10) == 0);
	CHECK(clamp_int(42, 0, 10) == 10);
}

static void test_max_of_finds_last(void)
{
	int xs[] = { 1, 4, 2, 9 };
	CHECK(max_of(xs, 4) == 9);
}

int main(void)
{
	test_clamp_below_and_above();
	test_max_of_finds_last();

	if (failures > 0) {
		fprintf(stderr, "%d check(s) failed\n", failures);
		return 1;
	}
	puts("all tests passed");
	return 0;
}
```

Notes:

- **`#cond`** turns the condition's source text into a string, so a failure prints the exact expression. `__FILE__` and `__LINE__` say where.
- **`do { ... } while (0)`** makes the macro behave like one statement, so `if (x) CHECK(y); else ...` works.
- **One small function per behavior**, named for what it proves. When `test_reset_reuses_buffer` fails, the name tells you what broke.
- **`static` on a function in C means "private to this file"** (internal linkage). It has nothing to do with C#'s `static`. Here it keeps test helpers from clashing with names in the code under test.
- **`assert()` from `<assert.h>`** also works, but it stops at the first failure, and compiling with `-DNDEBUG` turns it off completely. Never build tests with `-DNDEBUG`.

### What failures look like

A wrong answer (a bug that makes `clamp_int` return `lo` when the value is above the range):

```
./test_mathx
test_mathx.c:24: CHECK failed: clamp_int(42, 0, 10) == 10
1 check(s) failed
make: *** [Makefile:13: test] Error 1
```

A memory bug (a test that calls `max_of(xs, 5)` on a 4-element array). ASan aborts the program, which also fails the run:

```
==7736==ERROR: AddressSanitizer: stack-buffer-overflow on address 0x7a98b4700070 ...
SUMMARY: AddressSanitizer: stack-buffer-overflow .../mathx.c:16 in max_of
make: *** [Makefile:13: test] Error 1
```

### The sanitizer flag your done-when list needs

ASan always aborts on an error, but **UBSan, by default, prints a report and keeps running.** Your test can then exit 0, and `make test` passes with undefined behavior in it. From Debian:

```
$ gcc -fsanitize=undefined ovf.c && ./a.out; echo "exit=$?"
ovf.c:3:48: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
still running, y=-2147483648
exit=0

$ gcc -fsanitize=undefined -fno-sanitize-recover=all ovf.c && ./a.out; echo "exit=$?"
ovf.c:3:48: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
exit=1
```

So add **`-fno-sanitize-recover=all`** to your test build. Then "all passing cleanly" means what it says.

## 5. Applying it to the arena

Suggested layout for `unit1/1.1-c/arena/`:

```
arena.h        the API from session 1
arena.c        the implementation
test_arena.c   one test function per behavior, CHECK macro, exit status
Makefile       all, test, clean; CFLAGS from the done-when list plus -fno-sanitize-recover=all
```

Tests to write, one per done-when item:

- **Alignment:** allocations with align 1, 2, 4, 8, 16 and a large one such as 64, interleaved with odd sizes. Check every pointer with `(uintptr_t)p % align == 0`.
- **Bad alignment:** align 0, 3 and 12 each return `NULL`.
- **Exhaustion:** fill the arena exactly, check the next allocation returns `NULL`, and check the earlier pointers still work.
- **Reset and reuse:** after `arena_reset`, an allocation succeeds again at the start of the buffer.
- **Overflow:** `SIZE_MAX`, `SIZE_MAX - 1`, and a size just over the remaining capacity all return `NULL`, both on a fresh arena and on one that's partly full.

Write a test, watch it fail, then make it pass. Run `make test` under both `CC=gcc` and `CC=clang`; the compilers disagree about UB often enough to be worth it.
